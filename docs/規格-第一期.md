# NovelSystem 第一期規格

狀態：第一期已落地（Electron 桌面版；本機無 Rust，故未用 Tauri）。地圖釘點與行為推演仍為第二期。  
對象：單人長篇小說作者。  
介面語言：繁體中文。  
一份專案 = 一本書。多本書用多個專案資料夾。

---

## 1. 產品定位

本機桌面寫作工具。手稿與故事聖經只存在你電腦上。離線可寫、可改結構、可查角色與世界觀。連網只用於審閱（語言校稿、設定／禮儀檢查、從新章抽出待確認資料）。

它不是網文平台、不是協作編輯器、不是自動寫手。模型不直接往正文或聖經裡寫入任何內容；一切變更經你確認。

## 3. 第一期目標與非目標

### 目標（做完後你能做的事）

1. 在不受干擾的寫作區寫一章，即時看到章／場／全書字數。
2. 用卷 → 章 → 場 組織全書，每章、每場有概要。
3. 維護主線／明線／暗線／伏筆，並看到某條線在哪些場出現、是否已回收。
4. 維護帶時間的角色卡、關係、經歷、知情範圍。
5. 維護世界觀：禮儀、民生、勢力、地點、規則體系，以及專有名詞／稱呼。
6. 在時間軸上看到事件先後。
7. 存檔後啟動審閱；你接受語言修改、勾選資料變更後，聖經才更新。
8. 存檔留下章級快照，改壞可以還原。

### 非目標（第一期明確不做）

- 地圖上擺圖標、測距、旅行路線
- 角色行為推演沙盒
- 獨立的「文風樣本」管理頁
- 多人協作、雲端同步、帳號系統
- 自動續寫、按大綱生成章節
- 排版出版（精美 DOCX／EPUB 導出可列第二期；第一期只出純文字／Markdown）
- 系列宇宙（多書共享世界）

## 4. 核心概念

資料不是十個互不相干的筆記本，而是同一張網。場景是交會點。

```
時間點 ── 場景 ── 地點
            │
     ┌──────┼──────┐
   在場角色  視角  線索節點
     │              │
  知情／關係      伏筆埋／收
     │
   勢力／地位／稱呼
```

- **卷／章／場**：書的樹狀結構。寫作在章上進行；場切分章的正文。
- **線索**：橫切結構的線。一場可以碰到多條線。
- **時間點**：全書共用的順序軸。場、角色狀態、角色事件、線索節點都指向時間點。
- **聖經**：角色、世界、線索、詞表。來源是你手寫的條目，加上你確認過的「待確認變更」。
- **推演**（第二期）：假設，不是已發生。

## 5. 資料模型

以下為邏輯模型。實作可用 SQLite 表，名稱可對應轉換。

### 5.1 專案

- `id`, `name`, `created_at`, `updated_at`
- `timeline_mode`：`relative`（預設）或 `calendar`
- `word_count_mode`：見 §7.1
- `api` 相關不進專案檔，進本機設定

### 5.2 時間點 `TimePoint`

- `id`
- `sort_key`：可插入的數字序（例如 1000、2000；兩點之間插入用中值）
- `label`：顯示名，如「開篇」「決裂當夜」「入京第一年春」
- 可選曆法欄位：`era`, `year`, `month`, `day`, `season`, `hour`
- `notes`

規則：

- 第一期以 `sort_key` 為準，曆法欄位只是標籤，不做曆法運算。
- 任何「發生在何時」的資料都必須指向一個 `TimePoint`，禁止各表自填自由文字日期當唯一依據。
- 可建時間點而不掛事件，作為書籤。

### 5.3 結構

**Volume**：`id`, `title`, `order`, `summary`

**Chapter**：

- `id`, `volume_id`, `title`, `order`, `summary`
- `status`：`draft` | `in_review` | `final`
- `body`：該章完整正文（寫作區編的就是這份）
- `word_count`：由正文計算，不手填

**Scene**：

- `id`, `chapter_id`, `order`
- `title`（可空）
- `summary`
- `time_point_id`（可空，未定時標「時間未設」）
- `location_id`（可空）
- `pov_character_id`（可空；空 = 未指定或全知）
- `word_count`
- `body_from`, `body_to`：對應章正文中的字元區間；或改為在正文中插入場景分隔符，由分隔符解析出區間

**ScenePresence**：`scene_id`, `character_id`（在場，含未說話者）

**SceneThread**：`scene_id`, `thread_id`, 可選 `beat_id`

章與場的正文關係（寫作體驗關鍵）：

- 寫作區編的是**整章連續正文**，不是一場一個框。
- 章內用場景分隔（可見的分隔線，底層可為 `---` 或內部標記）切成一到多場。
- 新章預設只有一場，涵蓋全文。你加分隔線才變成多場。
- 刪分隔線則場合併，元資料保留較前一場的，並提示衝突（例如兩場地點不同）。
- 字數：場 = 該段正文；章 = 各場合計；卷／書往上加總。

### 5.4 線索

**Thread**：

- `id`, `name`, `summary`
- `type`：`main`（主線）| `overt`（明線）| `covert`（暗線）| `foreshadow`（伏筆）
- `status`：`planted` | `active` | `paid_off` | `abandoned`
- `parent_thread_id`（可空；例如某暗線從屬於主線）

**ThreadBeat**：

- `id`, `thread_id`
- `kind`：`plant` | `progress` | `payoff` | `abandon`
- `time_point_id`, `scene_id`（可空）
- `summary`
- 伏筆建議至少有一個 `plant`，回收時加 `payoff`。沒有 `payoff` 且狀態仍為 `planted`/`active` 的伏筆，在全書檢視裡列為「未回收」。

### 5.5 角色

**Character**（相對穩定的識別資料）：

- `id`, `name`
- `aliases`：別名、 titile 稱呼用名
- `gender`
- `appearance`：外貌（可隨時間用狀態覆蓋）
- `personality`：性格
- `speech_pattern`：聲口、用詞習慣、禁用語
- `goals`：動機與目標
- `notes`
- `color`：時間軸／關係圖用的標記色（可選）

**CharacterState**（帶時間的快照，查某場時取「該時間點或之前最近一筆」）：

- `character_id`, `time_point_id`
- `age`
- `status_title`：地位、官職、門派身份等
- `faction_id`（可空）
- `location_id`（可空，常駐地）
- `alive`：`true` | `false`
- `appearance_override`, `notes`

**CharacterEvent**：

- `character_id`, `time_point_id`, `scene_id`（可空）
- `summary`：經歷摘要

**Relationship**（有向，可互逆建兩筆）：

- `from_id`, `to_id`
- `type`：`kin` | `master_disciple` | `romantic` | `friend` | `enemy` | `lord_vassal` | `other`
- `label`：如「嫡兄」「師尊」「表面盟友」
- `start_time_id`, `end_time_id`（空 = 仍有效）
- `notes`

**Fact**（世界上的一條可知資訊）：

- `id`, `statement`
- `about_ids`：關聯角色／地點／勢力等
- `is_secret`
- `true_in_canon`：預設 true；角色可以「誤信」假資訊（`believed` 與事實分離）

**CharacterKnowledge**：

- `character_id`, `fact_id`
- `learned_at_time_id`, `learned_in_scene_id`（可空）
- `believed`：是否相信
- `forgotten`：是否已遺忘

審閱「不該知道卻說出來」：若該場時間點上，角色沒有對應 `CharacterKnowledge` 且 `believed=true`，卻在正文使用了該事實，則報問題。第一期允許漏檢（沒建 Fact 就查不到），不允許誤報到你已標明「已知」的情況被當成洩密。

### 5.6 世界觀

分類是一等的，條目掛在分類下。預設分類可改名、停用、新增。

預設分類：

| 分類 | 實體強度 | 說明 |
|---|---|---|
| 禮儀 | 條目 + 規則 | 場合、對象、應有行為、違禮後果 |
| 民生 | 條目 | 貨幣、物價、衣食住行、習俗 |
| 勢力 | 一等實體 | 門派、朝廷、商幫、國家 |
| 地點 | 一等實體 | 可掛從屬地點；第一期不顯示地圖，但保留座標欄 |
| 規則體系 | 一等實體 | 境界、魔法代價、科技限制、破格後果 |
| 其他 | 條目 | 自訂 |

**Faction**：

- `id`, `name`, `summary`, `hierarchy_notes`
- `parent_faction_id`（可空）
- 控制的地點用 Location 的 `controlling_faction_id` 反指

**Location**：

- `id`, `name`, `parent_id`（可空，如「東城」屬於「京城」）
- `summary`
- `controlling_faction_id`
- `map_x`, `map_y`：可空；第一期不在 UI 呈現，第二期釘圖用
- `map_image_id`：可空；預留給世界地圖圖檔

**EtiquetteRule**：

- `id`, `name`
- `context`：場合（朝會、私宴、戰場、師門）
- `from_role` / `to_role`：地位或輩分（可對應勢力職級、關係類型）
- `required`：應做／應用的稱呼或動作
- `forbidden`：禁止
- `consequence`：違禮後果（敘事用，也可給審閱當提示）

**LivelihoodEntry**：`id`, `title`, `body`, 可選關聯地點／勢力

**RuleSystem**（規則體系）：

- `id`, `name`, `kind`：`cultivation` | `magic` | `technology` | `other`
- `summary`
- 境界／等級：`RuleRank[]`，有序（如練氣 → 築基 → 金丹）
- 約束：`RuleConstraint[]`，每條有 `statement`、`applies_to`（境界／身份）、`violation_note`
- 角色的 `status_title` 或另設 `CharacterState.rank_id` 可指向某個 `RuleRank`（第一期建議加上 `rank_id`，方便破格檢查）

**WorldEntry**（通用條目，給民生與「其他」）：

- `id`, `category`, `title`, `body`, `linked_ids`

世界觀會隨劇情變：需要時間性的條目（誰統治某地、某條禁令何時頒布）用 `effective_from_time_id` / `effective_to_time_id`。第一期勢力控制地點、禮儀、規則約束支援這對欄位；純說明性民生條目可省略。

### 5.7 專有名詞與稱呼

**Term**：

- `id`, `surface`（正文裡出現的寫法）
- `normalized`（標準寫法）
- `kind`：`person` | `place` | `faction` | `title` | `technique` | `item` | `address` | `other`
- `linked_entity_type` + `linked_entity_id`（可空）
- `forbidden_variants`：已知錯寫
- `notes`

角色名、別名、地名、勢力名在建立實體時自動進詞表。你可再補功法、器物、特殊稱謂。

**AddressRule**（稱呼）：

- `id`
- `speaker_spec`：角色 id，或角色地位／關係類型
- `addressee_spec`：同上
- `term`：閣下、師兄、大人、你、汝……
- `formality`：`high` | `neutral` | `low` | `intimate`
- `notes`

審閱用 AddressRule + EtiquetteRule + 當場關係／地位，檢查稱呼是否失禮或前後不一。

### 5.8 版本

**ChapterSnapshot**：

- `id`, `chapter_id`, `created_at`
- `body`（當時全文）
- `trigger`：`save` | `restore` | `apply_review`
- `note`（可空）

規則：

- 正文相對上一快照有變更才在存檔時新增一筆（避免空按存檔刷一堆相同版本）。
- 還原前先把「還原前的現況」再存一筆 `restore` 快照，避免還原後無法回到還原前。
- 第一期不做跨章對比 UI；列表顯示時間與字數，可預覽、可還原。
- 保留策略：預設全留。若單章快照超過 50 筆，提示可刪中間檔、留首尾與最近 20 筆（手動確認後才刪）。

### 5.9 審閱與待確認

**ReviewJob**：

- `id`, `chapter_id`, `snapshot_id`（對應送審的那一版正文）
- `status`：`queued` | `running` | `done` | `failed` | `cancelled`
- `created_at`, `finished_at`, `error`

**ReviewIssue**（語言或連貫性問題）：

- `id`, `job_id`
- `kind`：`language` | `continuity`
- `subtype`：病句、標點、用詞、稱呼、知情、禮儀、破格、角色行為、時間矛盾、名詞不一……
- `severity`：`info` | `warn` | `error`
- `scene_id`（可空）
- `span_start`, `span_end`：相對於送審正文
- `original`, `suggestion`（語言類才有建議句；連貫性類可空）
- `explanation`
- `status`：`pending` | `accepted` | `rejected` | `ignored`
- 接受語言建議時，把建議寫入正文對應區間（見 §8），不整章覆寫。

**PendingChange**（聖經變更提案）：

- `id`, `job_id`, `chapter_id`, `scene_id`
- `action`：`create` | `update` | `link`
- `entity_type`：character / state / event / relationship / knowledge / location / faction / etiquette / rule / term / thread / beat / time_point …
- `target_id`（update 時）
- `payload`：建議寫入的欄位
- `reason`：從哪句正文抽出
- `status`：`pending` | `accepted` | `rejected`
- 接受後才寫入對應表。拒絕則保留紀錄，同一章再審時盡量不要重複提相同提案（用 payload 雜湊去重）。

## 6. 介面架構

桌面單一視窗。預設三欄，寫作區可一鍵進入「只留正文」（獨立寫作區）。

```
┌──────────────┬──────────────────────────┬─────────────────┐
│ 結構         │ 寫作區                    │ 本章上下文       │
│ 卷／章／場    │ 章標題                    │ 本章概要         │
│              │ 正文                     │ 本場：時間地點   │
│ 聖經入口      │ 場景分隔線                │ 在場、視角、線索 │
│ 角色／世界    │                          │ 字數             │
│ 線索／詞表    │                          │                 │
│ 時間軸        │                          │                 │
└──────────────┴──────────────────────────┴─────────────────┘
底列：全書字數  本章字數  存檔狀態  審閱狀態
```

### 6.1 獨立寫作區

- 隱藏左右欄、工具列收成極簡（存檔、字數、離開專注）。
- 快捷鍵進入／離開。
- 離開後左右欄狀態恢復。
- 專注模式仍可存檔；存檔規則與平常相同。

### 6.2 聖經各頁

獨立頁面，不塞進寫作右欄：

- 角色：列表 + 卡片（基本資料、狀態時間線、經歷、關係、知情）
- 世界：分類瀏覽；勢力／地點／規則／禮儀用表單，民生用條目
- 線索：線列表 + 節點；未回收伏筆置頂
- 詞表：名詞與稱呼規則
- 時間軸：縱向時間，節點可篩選（角色／線索／場）

右欄「本章上下文」只讀加可點連結（點角色開卡片），不在右欄裡長篇編輯聖經。

### 6.3 審閱介面

存檔成功且審閱完成（或失敗）後，用面板或覆蓋層呈現，不跳走寫作區：

1. 語言問題：原文片段 + 建議 + 說明；逐條接受／拒絕／略過
2. 連貫性問題：說明 + 跳到正文位置；通常沒有自動改句，只有「已知悉」
3. 待確認變更：勾選後「套用所選」

可隨時「對本章再跑一次審閱」（對目前正文，不強制先手動存；若未存則先自動存檔再送審）。

## 7. 模組規格

### 7.1 字數

不是獨立模組。寫作區底列與結構樹旁顯示。

預設：**不含空白、含標點的字元數**（接近華語網文習慣）。  
可在專案設定切換：

- 只計漢字與假名等
- 含空白總字元

場、章、卷、書都用同一規則。目標字數（章目標、書目標）第一期要做：可填、顯示進度，不做催更日曆。

### 7.2 結構與概要

- 樹可拖曳排序、可把章移到另一卷。
- 章、場都有概要欄。場概要可手寫；審閱抽出的概要走待確認變更，不直接覆寫。
- 刪章：進回收（第一期可做專案內「已刪章節」列表，30 天或直到你清空；避免誤刪無快照可救的結構）。

### 7.3 線索與伏筆

- 建立線時選類型。
- 在場的上下文或線索頁，把本場掛到某條線，並可加一個 beat。
- 伏筆檢視：埋設場 → 後續提及 → 回收場。未回收列表可按最後出現時間排序。

### 7.4 角色卡

建立角色時填：名、性別、目前年齡與地位（寫成「當前」狀態，掛在你指定的時間點，預設為時間軸最早或「開篇」）。

卡片分頁：

1. 資料（含聲口、目標）
2. 狀態沿革（年齡、地位、所屬、生死）
3. 經歷
4. 關係
5. 知情與秘密

關係從任一方卡片都能看到（出邊與入邊）。

### 7.5 世界觀

- 左側分類，右側條目。
- 地點樹狀（父／子）。第一期地點沒有畫布；列表與詳情裡座標欄隱藏。
- 規則體系：先建體系，再加有序境界，再加約束條文。角色狀態可選所在境界。
- 禮儀規則盡量結構化（場合、對象、應做、禁止），不要只有一篇散文，否則審閱用不上。

### 7.6 詞表與稱呼

- 自動：角色、別名、地點、勢力、境界名稱寫入 Term。
- 手動：補功法、器物、特殊寫法、錯寫。
- 稱呼規則單獨列表，審閱時優先於「通用禮貌」。

### 7.7 時間軸

- 縱向列表，依 `sort_key`。
- 每點顯示：標籤、掛上的場、角色事件、線索節點。
- 可插入點於兩點之間。
- 篩選：某角色、某條線、只看場。
- 第一期不做甘特圖、不做「一天內鐘點衝突」的自動物理檢驗；若兩場時間點順序與章順序明顯相反，審閱可警告（章序 vs 時間序）。

## 8. 存檔與審閱管線

這是第一期的主工作流。

```
按存檔
  │
  ├─ 立刻寫入章正文到專案庫
  ├─ 若正文有變：寫 ChapterSnapshot
  └─ 回傳「已存檔」（不開網路也不該失敗）
        │
        └─ 若本機已設定 API 金鑰：排隊 ReviewJob
              │
              ├─ 組上下文（見下）
              ├─ 模型回傳：語言問題、連貫性問題、待確認變更
              └─ 寫入 ReviewIssue / PendingChange
                    │
                    └─ 通知「本章審閱完成」
                         │
                         ├─ 語言：逐條接受 → 只改對應 span
                         ├─ 連貫性：已知悉／拒絕
                         └─ 變更：勾選套用 → 寫入聖經
```

### 8.1 存檔失敗與審閱失敗分離

- 磁碟／資料庫失敗：明確說存檔失敗，不開審閱。
- 無金鑰或離線：存檔成功，底列顯示「未審閱（離線或未設定金鑰）」。
- 審閱失敗：存檔仍有效，可重試。不得留下半套寫入聖經的變更。

### 8.2 送審上下文（控制篇幅）

每次只對**一章**送審。上下文包含：

1. 本章全文（必備）
2. 本章各場元資料：時間、地點、在場、視角、掛線
3. 在場角色的卡片摘要：性格、聲口、該時間點狀態、與在場他人的有效關係、相關知情（秘密與本章可能用到的事實）
4. 本章地點的禮儀、當地勢力、適用規則約束
5. 本章出現、且詞表裡有的專有名詞與稱呼規則
6. 本章掛上的線索與其最近幾個 beat
7. 風格參照：最近 1～2 章 `status=final` 的正文各截前 N 字（N 建議 800～1500）。若沒有已定稿章，只用本章。不做文風樣本庫。

上下文超長時的裁剪順序：先縮已定稿章，再縮未在場角色，再縮未引用的世界條目。本章全文不裁。

### 8.3 模型輸出必須結構化

禁止「一段修改後的全文」直接當結果。必須是：

- issues[]：類型、區間、原文、建議（可空）、說明
- pending_changes[]：實體類型、動作、payload、依據句

語言建議的約束寫進提示：

- 儘量保持句長、文白比例、稱呼習慣
- 不把方言／古語「現代化」
- 不增刪情節
- 標點依中文慣例（「」『』、《》、頓號、句號在引號內外等），但作者若在整章穩定使用非常規標點，以本章慣例為準

接受語言建議的套用方式：依 span 替換。若你在審閱期間又改了正文導致 span 對不上，該條標為「已過期」，不得亂插入。

### 8.4 抽出資料的原則

模型可以提議，不可以當真相：

- 新出場人物 → 建角色（最少：名、性別未知可空）
- 地位／年齡變化 → CharacterState
- 新經歷 → CharacterEvent
- 關係變化 → Relationship（含開始時間 = 本場時間）
- 有人得知秘密 → CharacterKnowledge
- 新地名／勢力／功法 → 對應實體 + Term
- 新伏筆句 → foreshadow thread 或既有線的 plant beat
- 回收已有伏筆 → payoff beat

不自動改 `Chapter.status` 為 final。你自己標定稿。

### 8.5 角色行為與禮儀檢查（原需求 8、9）

連貫性檢查器看：

| 檢查 | 依據 |
|---|---|
| 行為是否像這個人 | personality、goals、speech_pattern、近期事件 |
| 是否知道不該知道的事 | CharacterKnowledge + Fact |
| 稱呼與禮儀 | AddressRule、EtiquetteRule、當場地位與關係 |
| 是否破規則體系 | RuleConstraint、角色境界 |
| 死人出現、時間倒錯 | CharacterState.alive、TimePoint 與章序 |
| 名詞錯寫 | Term.surface / forbidden_variants |

此類問題預設只報告，不自動改情節。

## 9. 桌面、檔案與技術預設

這些是實作預設，若你要換技術可以在確認規格時改。功能行為不依賴某一套框架。

### 9.1 形態

- Windows 桌面應用（安裝包或可攜資料夾）
- 建議技術：Tauri 2 + TypeScript Web 介面 + SQLite
- 理由：寫作區需要成熟的網頁編輯器；殼層小；檔案與 SQLite 走本機；沒有強制雲端

### 9.2 專案檔

一個專案 = 一個資料夾，例如 `F:\Novels\某書\`：

```
某書/
  project.sqlite      # 聖經、結構、正文、快照、審閱
  media/              # 第二期地圖圖檔；第一期可先建立空目錄
  exports/            # 你匯出的 md/txt
```

用「開啟專案資料夾／建立專案」進入。最近開啟列表只存在本機設定，不進專案檔。

正文存在 SQLite，匯出時才生成 Markdown（一卷一檔或一章一檔，可選）。第一期不把 Markdown 當主存檔，避免雙份真相。

### 9.3 設定與金鑰

本機設定（非專案內）：

- API 金鑰放作業系統憑證庫或加密設定，不寫進專案、不進 git
- 提供者預設為 SpaceXAI（xAI，`https://api.x.ai/v1`），模型可在設定裡改名
- 無金鑰時全功能可寫，審閱按鈕提示去設定

寫作不經伺服器中轉。審閱時本章與 §8.2 的上下文會送到該 API。這是本機工具仍會出網的唯一路徑，須在設定頁寫清楚。

### 9.4 編輯器

- 章正文用富文本或 Markdown 擇一。第一期建議 **Markdown 原文模式**（可預覽），場景分隔為獨立區塊，不依賴複雜排版。
- 須支援大量中文、長章（單章數萬字）流暢捲動。
- 搜尋取代限本章；全書搜尋第一期要做（搜正文與聖經標題）。

### 9.5 備份

第一期：版本快照已覆蓋「改壞一章」。  
另在設定中提供「複製整個專案資料夾」的手動備份入口即可，不做雲備份。

## 12. 規格內的預設（可在確認時改）

下列不是功能增刪，是我代選的預設。你要改請直接說。

## 13. 驗收（第一期完成的定義）

用一本虛構短篇走完下列路徑即算第一期完成：

1. 新建專案，建兩卷、三章；其中一章用分隔線切成兩場。
2. 建兩個角色、一條關係、一處地點、一個勢力、一條禮儀、一個規則體系（至少兩層境界）、一條伏筆。
3. 給角色各一條知情（其中一條是秘密）。
4. 寫一章正文，提到秘密、稱呼、境界。
5. 存檔：無網時顯示已存、未審閱；有金鑰時產出語言問題與待確認變更。
6. 拒絕部分語言建議、接受部分；套用一筆「新經歷」到角色卡；角色卡與時間軸出現該事件。
7. 還原到存檔快照，正文回到套用建議之前。
8. 專注模式只見正文；離開後結構樹仍在。
9. 全書搜尋能找到正文中的一句與角色名。
10. 匯出該章 Markdown。地圖頁與推演入口不存在或標為未開放。
